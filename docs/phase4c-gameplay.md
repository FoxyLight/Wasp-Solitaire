## Inputs, presentation and state flow

GameBoardHost observes GameViewModel.uiState and lastResult with collectAsStateWithLifecycle. User actions submit GameIntent; GameController serializes them under its existing Mutex. ClassicWasp remains the only authority for legal moves, reserve, reveals, completed runs, victory and Undo. Successful state changes are published only after repository.commit confirms the next revision. Immutable sessions, all history, compare-and-swap and failed-write behavior remain intact. No rules or alternate game model were added to Compose.

- Tap any exposed card to select it plus its whole attached tail. All legal destination outlines come from GameUiState. Tap a highlighted column to commit MoveTo; no destination is chosen automatically. Tapping a different source switches selection; tapping the same selected card, Cancel or Back clears it without history. A tap on a different unhighlighted card switches selection, rather than attempting an implicit move.
- Long press a face-up card to lift its complete tail into a root overlay. BoardDrag stores only temporary coordinates and the immutable preview; the original tail is dimmed. The highlighted destinations still come from the controller. The dragged group preserves order, even when internally unordered. The drag label identifies the group and candidate column without relying solely on color.
- Normal vertical swipes scroll; dragging starts only after long press. During a drag, scrolling and controls pause. Every column has a drop zone spanning the full current tableau height, so a player can scroll a deep source into view and drag horizontally into any column, including short or empty ones. A gap, outside-board drop or cancelled pointer discards the preview without a commit. Illegal column drops go to the engine and preserve board/history. The preview is transient and is discarded on recreation, a revision change or pointer cancellation. Drops carry expectedRevision so queued stale drops cannot commit onto a different board.
- Undo, Hint and Deal 3 remain pinned above the scrolling board; Restart, New Game and selection Cancel are immediately below, or in More for windows shorter than 400dp. Standalone targets are at least 48dp. Buttons expose enabled/disabled states and text labels. Deal 3 is available with legal moves or empty columns and disables after use; Undo restores it. Hint displays the controller's legal action or reserve fallback without a write. No hint yields factual no-tableau-moves feedback, never defeat.
- Feedback for invalid input, cancelled drops, stale actions and failed writes is displayed above the board with a polite live region. Completed suited runs stay in place and an engine-confirmed won state displays victory; Undo remains available. No timer, statistics, solver, automatic loss, foundation extraction or extra mode was added.

## Restart and New Game semantics

Added RequestRestart, RequestNewGame, ConfirmReset(revision) and CancelReset to the existing controller. PendingReset(kind, revision) is transient GameUiState; asking/cancelling a confirmation never touches session/history/revision. It survives configuration changes with the ViewModel, but is not durable. The modal blocks accidental board input. Confirmation requires its originating revision; a later successful action clears it, and stale confirmation/drag inputs are rejected.

Restart confirms whenever actions/history would be discarded, then restores the actual earliest state in the current full Undo history (or the untouched current state). It deliberately does not recreate a saved initial deal solely from a seed. It preserves the seed/deal, restores reserve and face states, resets net action count and clears history/selection/hint. A missing action-zero initial snapshot returns a visible failure instead of guessing. Restarting an untouched deal needs no destructive confirmation.

New Game asks for confirmation while the game is in progress, including an untouched deal. After victory it may proceed directly. Only confirmed execution generates a seed through an injectable supplier (SecureRandom by default) and ClassicWasp.newGame. If the supplier repeats the current seed, one bit is toggled to ensure a different seed. New Game clears prior history/selection/hints and resets net action count. No new game-start/win statistics are implemented. Phase 5 must supply durable deal identity and exactly-once statistics semantics separately.

Both reset operations use the same revision-incrementing repository write path as engine-accepted actions. A storage failure/conflict leaves the old session and full Undo history unchanged; a failed confirmed reset leaves its dialog available for retry/cancel. Reset itself is not an undoable gameplay action. Revision stays monotonic even though net action count resets. No repository interface change or storage shortcut was introduced.

## Limitations and deferred work

The overlapping overview still has small card strips. Expanded interactive inspection, comprehensive TalkBack/non-drag workflows, final contrast and broad physical-device validation remain Phase 4D. Long-press dragging has no edge autoscroll; a source can be scrolled into view before a horizontal drop to any full-height column target. Animation is a direct lift/snap, without new sound/haptic settings. Room/atomic durable storage, process-death recovery, DataStore, lifecycle timer and the four statistics remain Phase 5. No autosave claim, account, release preparation, production identity/signing change or publication is included. No blocking owner product decision is currently identified; owner code/visual review and explicit merge approval remain required.
Physical validation found the older Espresso 3.6.x harness blocked all 13 tests before view interaction on Android 17 (InputManager.getInstance reflection). Test-only dependencies were updated to stable Espresso 3.7.0 and AndroidX Test JUnit 1.3.0, using the [officially documented compatibility fix](https://developer.android.com/jetpack/androidx/releases/test). Application runtime dependencies and rules are unchanged; rerun outcomes are recorded in the PR.

Focused visual review is part of the milestone gate: it caught cramped 200%-text control labels and excessive landscape toolbar space despite passing behavioral tests. The final controls use reduced horizontal padding, secondary actions move into a More menu below 400dp window height, and BoardGeometry caps card size to the actual scroll viewport as well as width. A dedicated JVM case covers whole-card reachability in a short viewport. Screenshot capture waits for native popup/ripple transitions to settle; tests still assert state and interaction outcomes independently of capture.
